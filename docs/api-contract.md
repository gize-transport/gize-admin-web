# API contract between gize-admin-api and gize-admin-web

**This file is identical in both repositories.** The backend repo owns it; the frontend copy is synced by `npm run contract:sync`. If the two copies differ, the backend's wins.

## Source of truth

- The backend's OpenAPI document is the **only** definition of the API: endpoints, request/response shapes, field limits, enums, error codes, pagination.
- The backend commits it as `openapi.json` at the repo root, regenerated by a script and checked in CI (a PR that changes the API without updating `openapi.json` fails).
- The frontend **never hand-writes API types**. It generates them from a pinned copy of `openapi.json` with `openapi-typescript` and calls the API with `openapi-fetch`.

## Versioning and change rules

- All endpoints are under `/v1/`. Within `/v1` only **additive, backward-compatible** changes are allowed: new endpoints, new optional request fields, new response fields, new enum values the frontend handles with a default.
- **Breaking changes** (removing or renaming a field, endpoint or error code, making a field required, changing a type, tightening a limit) are blocked by CI (`oasdiff breaking`). They need: a ticket in both repos, a deprecation period (`deprecated: true` in OpenAPI for at least one release), and the frontend released first.
- Error `code` values are stable identifiers. New codes may be added; existing ones are never renamed or reused. CI blocks removing a code from `ErrorCode` or from an operation's `x-error-codes` (`scripts/contract_codes.py`).
- The backend tags each merge to `main` that changes the API as `api-vX.Y.Z` (semver: minor = additive, patch = docs/examples; major only for a breaking change the owner approved with the `breaking-change-approved` PR label). The tag's GitHub release has `openapi.json` attached. Tagging is automatic (`.github/workflows/contract-release.yml`).
- Error responses are `application/problem+json` (`Problem`, or `ValidationProblem` for `VALIDATION_FAILED`), and each one lists the codes it can carry in `x-error-codes`. `ErrorCode` is an enum in the schema.
- Every operation shows examples (GZ-061): each 2xx response its model's (a page with one item), each error response one per code it lists. The data is made up. The backend's test suite fails if any operation returns, in any test, a code its `x-error-codes` doesn't list.
- Errors any request gets, listed on no operation: `BAD_REQUEST` (400, a request the framework can't read), `CORS_PREFLIGHT_REJECTED` (400, a browser preflight from an origin or with a header not allowed), `METHOD_NOT_ALLOWED` (405); also `NOT_FOUND` (404) for a path that doesn't exist and `PAYLOAD_TOO_LARGE` (413) for a body over the limit, even on an operation that takes none.

## How the frontend stays in sync

1. `npm run contract:sync` downloads `openapi.json` and this file from the backend repo at a given tag (default: latest `api-v*` tag) using `gh`, writes `src/lib/api/openapi.json`, regenerates `src/lib/api/schema.d.ts`, and records the tag in `src/lib/api/CONTRACT_VERSION`.
2. Generated files are committed. CI regenerates them and fails if they differ (nobody edits them by hand).
3. A scheduled CI job runs daily: compares the pinned contract with the backend's latest tag and opens an issue `Contract update available: api-vX.Y.Z` with the diff.
4. Typecheck is the safety net: if the backend changed something the frontend uses, the build fails after sync, not in production.

## How work is coordinated

- Backend tickets are `GZ-xxx`; frontend tickets are `GZW-xxx`. Every frontend ticket lists the backend tickets it depends on.
- A frontend ticket that needs an endpoint that does not exist yet stops and requests a backend ticket; it never invents the endpoint. It may build against **mocks generated from the agreed OpenAPI** (MSW handlers typed from `schema.d.ts`) once the backend PR with that contract is merged.
- PR descriptions in both repos state the contract version they produce or consume.

## Shared conventions (summary – details in backend `docs/architecture.md`)

- JSON, snake_case fields; timestamps ISO 8601 UTC (the frontend displays Africa/Addis_Ababa). Schedule times of day (route times) are local Addis Ababa time, `"HH:MM"`, shown as they are.
- Auth: `Authorization: Bearer <Supabase access token>`; roles come from the backend, never from the token or the UI.
- Errors: RFC 9457 problem+json with `code` and `request_id`; the frontend shows a friendly message per `code` and always shows the request ID for support.
- Lists: `?limit=&cursor=` → `{ items, next_cursor }`, max 100.
- `Idempotency-Key` header (UUID) required on side-effecting POSTs; the frontend generates one per user action and reuses it on retry.
- `X-Request-ID` on every response.
