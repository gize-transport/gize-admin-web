# Architecture – admin portal

## Big picture

```
Browser ──▶ Next.js admin (Cloudflare Workers) ──HTTPS, Bearer token──▶ Gize Admin API (FastAPI) ──▶ Supabase Postgres
   │                 │
   └── Supabase Auth (sign in, session cookies via @supabase/ssr)
```

- The portal talks to **two** services only: Supabase Auth (sign-in/session) and the Gize Admin API (all data). It never queries Supabase tables directly.
- No business logic in the frontend: no price calculations, seat counting, launch or status rules, or permission rules beyond hiding UI for convenience. Seats taken/free, launch progress, which status moves a route allows and what blocks them (`status_changes`) and which months it can launch (`launch-months`) come from the API; the UI only displays them and explains the API's refusals.

## Auth flow

1. Sign-in page uses Supabase Auth (email + password). `@supabase/ssr` keeps the session in cookies; `middleware.ts` refreshes an expired session and verifies the token with `getClaims()` (locally with Supabase's asymmetric signing keys; by asking Supabase Auth with legacy symmetric keys), then sends signed-out visitors to `/sign-in?next=…`. If Supabase can't be reached when a check or refresh needs it, the visitor is treated as signed out. The browser reads the access token from those cookies to call the API, so they are **not** HttpOnly (owner decision, 2026-11-01): the protection is the strict nonce-based CSP (GZW-006), no `dangerouslySetInnerHTML`, no third-party scripts, and short-lived access tokens.
2. The API client reads the current access token from the Supabase session and sends `Authorization: Bearer …`. Tokens are never stored elsewhere.
3. After sign-in the app calls the API's "current staff" endpoint (`staff_me`) to get the role. If the API returns 403 (not a staff member or deactivated), sign the user out and show a clear message. After sign-in, `next` is followed only when it is a path on this site (`safeNextPath`). Signing in or out clears the TanStack Query cache. Sign out ends this browser's session only (revoked on the server); other devices stay signed in. A 401 from the API also signs this browser out before opening sign-in, so a token the API rejects can't leave someone stuck.
4. Role-based UI: navigation and buttons hidden for actions the role can't perform; every mutation still handles 403.

## Data fetching

- Client components with TanStack Query for lists, details and mutations (interactive admin screens). Server components for layout and static shell.
- Query keys per domain (`['routes', filters]`, `['route', id]`); mutations invalidate exactly the affected keys.
- Lists use cursor pagination from the API; filters and cursor live in the URL search params.
- Retries: queries retry network errors and 502/504 gateway errors up to 2 times with backoff, never on 4xx, 500 or 503. Mutations never auto-retry; a manual retry reuses the same `Idempotency-Key`.
- 429 and 503: show "try again in N seconds" from `Retry-After` (ProblemAlert countdown). 401: go to sign-in. 403: no permission.
- 409 on a change judged from data on screen (a route's `status_changes`, launch months): show the message, then invalidate and reload the route – the screen was a snapshot.

## Times

- **Timestamps** (`created_at`, `first_signed_in_at`, …) are ISO 8601 UTC; format them with next-intl in `Africa/Addis_Ababa` (`src/i18n/config.ts`).
- **Schedule times** (a route's four times: leaves A, arrives at B, leaves B, arrives at A) are local Addis Ababa times of day, `"HH:MM"`. Show and send them exactly as they are – never through `Date` or a time-zone conversion. Inputs use `<input type="time">` (value `HH:MM`).
- **Months:** individual riders start on the 1st of a month and launch dates are the 1st of a month; pickers offer whole months, and the API validates.

### Running against the local API

For manual work on screens with real data. Start the API as in the backend README ("Running the API for the frontend"), after its first admin and sample data (`python -m gize_api.cli.sample_data`: areas, corridors, companies, routes in every status reachable without riders, route requests). Then `npm run dev` with `NEXT_PUBLIC_API_BASE_URL=http://localhost:8000` and the same Supabase project's URL and publishable key (`sb_publishable_…`) in `.env.local`.

- The API's `CORS_ALLOWED_ORIGINS` lists `http://localhost:3000` only, so the dev server must run on port 3000. Playwright's server (port 3100) and unit tests never call the local API: they use MSW handlers typed from the generated schema (CI has no backend).
- Sign in with your own staff account (made admin with the backend's first-admin command). A signed-in user who isn't staff gets 403.

Public env vars only (`NEXT_PUBLIC_API_BASE_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (Supabase's publishable key; the legacy anon key is deprecated, and a secret key is refused), `NEXT_PUBLIC_SENTRY_DSN`), validated in `lib/env.ts`. No server secrets are needed by this app; if one ever is, stop and ask.

## Deployment

Cloudflare Workers via `@opennextjs/cloudflare` (GZW-006): `wrangler.jsonc` names the Worker (`gize-admin`) and its address, `open-next.config.ts` the adapter's settings, `npm run cf:build` builds it and `npm run cf:preview` runs it locally in the Workers runtime.

- **Production:** `https://admin.gizetransport.com` (a Workers custom domain on the `gizetransport.com` zone: Cloudflare creates its DNS record and certificate). CI's `Deploy (Cloudflare)` job deploys `main` after every other check passes, one deploy at a time.
- **PR previews:** the same job uploads each PR as a Worker version (not live) with a stable preview address, `pr-<number>-gize-admin.<account>.workers.dev`, posted on the PR. The API only answers origins on its `CORS_ALLOWED_ORIGINS`, so a preview loads data only if the API allows preview addresses (owner decision 2026-11-10: previews now, data once the backend allows them).
- **Settings:** the `NEXT_PUBLIC_*` values are GitHub repository **variables** (public: they are in the browser bundle), baked in at build; `CLOUDFLARE_API_TOKEN` (Workers scripts, Workers Routes, DNS edit and Zone read on `gizetransport.com` only) and `CLOUDFLARE_ACCOUNT_ID` are repository **secrets**, given only to the upload steps. A PR's own code builds and uploads in those steps, so anyone who can push a branch can reach the token: give write access only to people trusted with production. The token expires on 2027-11-10.
- **The first deploy** creates the `admin` record on the zone (replacing any record of that name without asking) and turns preview addresses on; PR previews start after it (until then the job says so and passes). Each production deploy first checks it is still `main`'s newest commit, so a slower older run never replaces a newer one.
- **No server secrets, no server cache:** the Worker renders pages and holds no data. Every page renders per request (below), so there is no Next.js incremental cache, queue or image service (both images are served as is).
- **Security headers:** `middleware.ts` gives each response a fresh nonce and the Content Security Policy built by `src/lib/csp.ts` (scripts only with the nonce and `'strict-dynamic'`, connections only to the site, the API, Supabase and Sentry, `frame-ancestors 'none'`, `upgrade-insecure-requests` when all of those are https). `next.config.ts` adds `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, a `Permissions-Policy`, HSTS (a year) and drops `X-Powered-By`.
- **Why no prerendering:** a nonce must be new for every response, and a page built ahead (cacheComponents' static shell, PPR) can't carry one (Next.js "Content Security Policy" guide). So `cacheComponents` is off and the root layout waits for the request (`connection()`): owner decision 2026-11-10, strict CSP over the prerendered shell. The portal's screens are drawn in the browser (`ClientOnly` in `(portal)/layout.tsx`, the sidebar still from the server): their data is fetched there, and a screen rendered on the server could hydrate after its data arrived and differ from its HTML (React #418, seen in CI). Zod runs `jitless` (`src/instrumentation-client.ts`), so its `new Function` probe never trips the policy.
- **Sentry** is browser-only (`src/instrumentation-client.ts`); the Worker reports nothing (it holds no data).
