# Architecture – admin portal

## Big picture

```
Browser ──▶ Next.js admin (Cloudflare Workers) ──HTTPS, Bearer token──▶ Gize Admin API (FastAPI) ──▶ Supabase Postgres
   │                 │
   └── Supabase Auth (sign in, session cookies via @supabase/ssr)
```

- The portal talks to **two** services only: Supabase Auth (sign-in/session) and the Gize Admin API (all data). It never queries Supabase tables directly.
- No business logic in the frontend: no price calculations, seat counting or permission rules beyond hiding UI for convenience.

## Auth flow

1. Sign-in page uses Supabase Auth (email + password). Session stored in HTTP-only cookies by `@supabase/ssr`; middleware refreshes it and protects `(portal)` routes.
2. The API client reads the current access token from the Supabase session and sends `Authorization: Bearer …`. Tokens are never stored elsewhere.
3. After sign-in the app calls the API's "current staff" endpoint to get the role. If the API returns 403 (not a staff member or deactivated), sign the user out and show a clear message.
4. Role-based UI: navigation and buttons hidden for actions the role can't perform; every mutation still handles 403.

## Data fetching

- Client components with TanStack Query for lists, details and mutations (interactive admin screens). Server components for layout and static shell.
- Query keys per domain (`['routes', filters]`, `['route', id]`); mutations invalidate exactly the affected keys.
- Lists use cursor pagination from the API; filters and cursor live in the URL search params.
- Retries: queries retry network errors up to 2 times with backoff, never on 4xx. Mutations never auto-retry; a manual retry reuses the same `Idempotency-Key`.
- 429: show "Too many requests – try again in N seconds" from `Retry-After`.

## Environments

| Env | API base URL | Supabase project |
| --- | --- | --- |
| Local | `http://localhost:8000` (backend running locally) or MSW mocks | Staging project |
| Staging | staging API URL | Staging project |
| Production | production API URL | Production project |

Public env vars only (`NEXT_PUBLIC_API_BASE_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_SENTRY_DSN`), validated in `lib/env.ts`. No server secrets are needed by this app; if one ever is, stop and ask.

## Deployment

Cloudflare Workers via `@opennextjs/cloudflare`; preview deployment per PR, production from `main`. Security headers (CSP, frame-ancestors none, referrer policy, nosniff) set in Next.js config. Check Cloudflare's current Next.js guide when setting this up.
